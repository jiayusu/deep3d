# 原提案审查：从架构远景到可开发的精密 CAD 系统

审查日期：2026-10-26。审查对象为用户提供的 8,811 行原稿，归档于 [original-proposal.txt](reference/original-proposal.txt)。下文的 `L` 均指该文件的原始行号。本文是设计审查记录，不代表对应能力已经实现或通过测试。

用户已明确第一产品方向为精密 CAD：B-Rep + OCCT，交付 STEP。因此，原稿中的城堡、游戏资产、Mesh 编辑和多内核路线保留为远景；本次开发基线围绕工业零件及受控装配建立。规范以本目录新的 CAD 基线与运行时协议为准，原稿作为只读历史材料。

## 应保留的架构决定

| L1081–1100、L1157–1162 | 稳定 ID 与路径分开；特征历史与操作历史分开 | 重命名、重排层级不改变身份，撤销不会偷偷篡改已有历史 |
| L1211–1239、L2432–2450 | 不可变几何产物，定义与求值分离 | 参数编辑可先保存，失败求值不覆盖上一次有效产物 |

## 需要修改的 18 项

### F01 · P0：首版产品范围需要替换，不能直接沿用城堡验收

**依据：** L44–180、L873–950、L5478–5531、L8679–8734。

原稿同时覆盖 Mesh、B-Rep、程序化建模和游戏场景，首实验又以建筑数量、部件数和 GLB 为主。这些指标不能证明精密 CAD 能力。首版限定 OCCT B-Rep、受控 Feature、尺寸与装配约束、STEP；用工业零件基准验收。Mesh 只作为从 B-Rep 派生的显示产物，不进入权威建模链。

### F02 · P0：几何适配器必须保留诊断和操作历史

**依据：** L1719–1723、L4445–4506、L4773–4913、L8642–8677。

“统一内核接口”仍不足以决定哪一层能提供错误与拓扑演化。采用 Python OCP 直接调用 OCCT 的适配器，逐操作收集完成状态、诊断、历史及完整性标记；build123d 可以辅助经过审查的构造函数，不能成为工程权威状态或公共任意脚本入口。Rust 负责协议与一致性，不先开发一套新的 Rust→OCCT 绑定。[OCCT 官方升级说明](https://dev.opencascade.org/doc/occt-7.8.0/overview/html/occt__upgrade.html)表明历史接口及其适用输入随版本变化，必须针对锁定版本验证。

### F03 · P0：单位、坐标与变换必须形成一个契约

**依据：** L1180–1195、L2288–2295、L3973–3994。

原稿以米、弧度为示例，当前 CAD 基线统一为 **mm / rad、右手系、Z 向上**。每个 IR、BREP manifest、测量报告及 STEP 导出均显式携带单位与坐标约定；外部单位在边界归一化。build123d 的形状没有内置单位，文档通常按毫米解释数值；辅助函数若接收角度制，必须显式转换。[官方单位说明](https://build123d.readthedocs.io/en/stable/build_part.html) 禁止通过 UI 显示值推断内核单位。

### F04 · P0：内核有效性不等于工业精度验收

**依据：** L557–606、L1281–1291、L5332–5367、L8554–8582。

`geometry.is_valid=true` 只能覆盖验收的一部分。每类零件应明确尺寸范围、允许公差、预期 solid 数量、闭合性、体积、孔径/孔距和装配关系。数值建模容差、设计验收公差、STEP 往返误差与预览三角化误差分别定义，不能共用一个 `tolerance`；显示截图不能替代精确 B-Rep 测量。

### F05 · P0：子拓扑引用需要失败契约，不能承诺普遍稳定

**依据：** L1456–1502、L4383–4443、L4445–4506、L4531–4630。

保留 feature/output 稳定 ID、操作历史与语义选择器，但不把 `Face_12`、OCCT 内存身份或一次遍历序号保存为永久引用。优先引用 datum plane、axis 和参数；必须选子形状时，绑定输入 artifact、选择器、预期类型及基数。历史不完整、零匹配、多匹配或语义校验失败时显式停止，不能把最近的面静默当成原面。倒角等操作只有在相应选择器和失败夹具通过后才能列为已支持。

### F06 · P0：IR 命令清单需要升级成可执行契约

**依据：** L1241–1334、L1687–1717、L3945–4012。

每个命令必须给出精确 schema、版本、参数边界、输入输出类型、读写键、错误码和后置检查。补齐事务内“先创建后引用”的规则、删除被引用特征的拒绝规则、递归删除是否显式、重设父节点是否保留世界变换等语义。`resolve_node(id)` 改为显式绑定 project/revision 的读取，避免验证和执行看到不同快照。

### F07 · P0：发布身份必须同时冻结定义、几何与证据

**依据：** L1009、L2373–2394、L2432–2450、L7734–7769。

原稿区分 Specification Revision 与 Materialization 是正确的，但只用 revision 指针仍可能让同一个已批准版本解析出不同几何。明确不可变 spec、不可变 materialization manifest、不可变 publication 三层；publication 绑定完整几何、证据与验证策略版本。进行中的求值状态可以变化，已经发布的解析结果不可原地补写或替换。

### F08 · P0：合并需要可信读集和重基验证

**依据：** L1550–1569、L1573–1591、L4286–4319、L7813–7836。

读集由服务端基于固定快照和受控查询产生，不能只接受 Agent 的声明。除属性外，记录集合成员关系、层级和约束作用域；否则会漏掉查询结果新增成员等冲突。首版保守处理：分支变化后重基受控命令并重新验证候选，必要时重算。独立部件可并行计算，但旧头下的几何与证据不能直接证明新头下合并合法。

### F09 · P0：分支 CAS 需要单调 generation

**依据：** L2388–2394、L2420–2428、L7748、L7767。

示例更新只比较 `head_revision`，未使用已有 `version` 字段；若回退后再回到相同 head，会出现 ABA 判断漏洞。冻结 `expected_head + expected_generation`，任何移动都递增 generation，更新影响行数必须为一。用户撤销通过后继提交或受审计的指针操作表达，不重写已有 revision。

### F10 · P0：STEP、BREP 与工程保存必须分别验收

**依据：** L2518–2520、L2610–2612、L3417–3463、L8722–8728。

STEP 为几何交付；BREP 为锁定内核环境下的几何产物；`.deep3d` 工程还需保存参数、Feature DAG、语义引用、版本和依赖。不能以 STEP 重导入后能显示，证明工程可继续参数化编辑。验收必须同时覆盖项目重开后修改参数重算、STEP 重导入测量，以及 BREP 产物完整性。[build123d 导入导出文档](https://build123d.readthedocs.io/en/stable/import_export.html)只能证明适配能力存在，不能替项目格式保存历史。

### F11 · P0：任务与计划的关系需要独立成员表

**依据：** L6975–7024、L7382–7417、L8049–8094。

`tasks.plan_revision_id` 把 task 固定在创建计划，而重规划示例又允许 `keep` 旧任务；新 current plan 下的领取条件会排除这些保留任务。改为稳定 task 身份与版本化 plan membership 分离，计划依赖边绑定成员关系。创建新计划时明确哪些成员保留、替换或删除，领取时检查当前计划成员资格及当前证据，不能直接重写旧 task 所属计划来补洞。

### F12 · P0：先用完整 epoch 失效规则，再做局部复用

**依据：** L6918–6922、L7048–7050、L7635–7666、L8047–8094。

“不立即废弃整个 Plan”与“旧 Attempt 必须重新授权”需要更具体的执行规则。首版控制变更采用保守完整 epoch 失效：撤销所有旧 epoch 的活动发布权；候选 artifact 和已接受历史保留，按新目标重新验证并建立适用性。暂停、目标更新与取消分别规定是否可重新授权，取消不得被恢复动作隐式逆转。局部 evidence 迁移作为后续优化。

### F13 · P0：人工审批不能占用计算租约等待

**依据：** L7351–7365、L7441–7448、L7761–7763、L8343–8388。

原稿的发布条件要求有效租约，审批可能持续数小时，续租例子又不包含 `waiting_human`。进入审批时保存候选并释放计算租约；审批绑定候选摘要、head/generation、goal/plan/control epoch、策略及有效期。批准后领取新的受保护发布租约，再检查全部条件；变化后使审批失效，不靠无限续租维持授权。

### F14 · P0：幂等发布需要定义响应丢失后的判定顺序

**依据：** L7427–7433、L7784–7811、L8623–8638。

原稿已经要求幂等记录、branch head、Task Accepted 同事务，应保留。补充：已授权调用方重试同一请求时，先查已提交的操作摘要；一致则返回原 publication，即使原租约已到期。只有未成功的请求继续走当前租约等检查；同键异内容拒绝。幂等键按租户、项目和操作类型限定，调用者仍须鉴权；事务提交前的操作记录不能伪装为成功。

### F15 · P0：上传与 GC 之间需要写入屏障

**依据：** L2452–2476、L3495–3512。

“先写不可变对象再提交引用”保留，但安全宽限期本身不足以证明并发 GC 安全。候选、上传和待发布对象需有数据库可见的保留/pin；最终发布事务确认对象仍可用且未被删除。首版关闭自动物理删除，仅列出待回收对象；完成 epoch/墓碑/写入屏障的故障验证后才启用删除。

### F16 · P0：可缓存不等于跨平台字节确定

**依据：** L1407–1427、L2316–2328、L3054–3101、L3251–3273。

Action key 必须包含规范化参数、完整输入、操作版本、OCCT/OCP 和构建环境标识、数值配置及随机种子。明确哈希字节布局、集合排序、默认值和非有限浮点拒绝规则；BREP 文件内容哈希只证明同字节，不能直接作为几何语义等价证明。相同 action key 产生不同结果时记录冲突并暂停该缓存项，不采用最后写入覆盖。初版先在锁定环境中资格验证。

### F17 · P1：首个垂直闭环应早于百万节点与高级优化

**依据：** L3537–3545、L3704–3716、L5971–6216、L6522–6593。

保留增量与性能方向，但百万节点、完整 SoA/GPU residency、动态查询、e-graph、72 小时城堡实验均不作为工业 CAD 首发阻塞项。先验证真实零件的 typed IR→OCCT→精确验收→原子发布→STEP→重开编辑，再增加两个 Agent 并发、目标更新、审批、故障恢复。微基准通过不能替代工业几何与端到端正确性验收。

### F18 · P0：参考工程和部署可用性不能写成既成事实

**依据：** L2979、L3463、L7516–7536、L7620、L8748–8774。

原稿多处明确为伪代码/接口草案，结尾声称整理了 ZIP，但本次输入仅提供文本，没有该 ZIP 或可运行实现；粘贴后的部分代码也丢失了格式。不能据此声称迁移、Temporal、并发或端到端已经完成。新方案需单独给出 schema、状态机、接口、故障测试和工业资格门槛，未来由实际仓库及测试证据记录完成度。

## 外部依赖核实的边界

目前只核实了公开的上游资料，没有安装或执行 OCCT/OCP/build123d，也没有完成目标操作系统上的 wheel 兼容性验证。开工时应锁定实际可安装、通过资格夹具的版本与镜像 digest，而非使用 `latest`。

build123d 官方版本配置可用于准备候选环境，但它不是项目执行基线的权威来源：[v0.13.0 配置](https://raw.githubusercontent.com/gumyr/build123d/v0.13.0/pyproject.toml)。绑定源码和底层库也不能统一写成单一许可：build123d 与 OCP 绑定仓库标注 Apache-2.0；OCCT 的库许可及附加例外需分别保留。[build123d 仓库](https://github.com/gumyr/build123d)、[OCP LICENSE](https://raw.githubusercontent.com/CadQuery/OCP/master/LICENSE)、[OCCT LGPL 文本](https://github.com/Open-Cascade-SAS/OCCT/blob/master/LICENSE_LGPL_21.txt)、[OCCT 附加例外](https://github.com/Open-Cascade-SAS/OCCT/blob/master/OCCT_LGPL_EXCEPTION.txt)

以上发现的关闭标准是：新规范中存在唯一、可测试的答案，并在实现后由相应测试或资格记录证明；仅增加一段“未来需要考虑”的文字不算关闭。
