# V0.1 验收注册与证据协议

基准日期：2026-10-27。目标验收日期：2026-11-01。本文落实用户的目标状态契约，数值均为预设门槛，不是系统现有成绩。

当前产物为**未冻结的注册草案**。它不启动任务、不批准后台执行、不包含观测成绩，也不证明 G1～G7 或 LH-001 已通过。正式冻结、运行器、独立检测器、种子资产和干净环境复现仍须实际实现与执行。

## 1. 文件及权威

| 文件 | 作用 |
| --- | --- |
| [registry.draft.json](../acceptance/v0.1/registry.draft.json) | 10 个自然语言案例、20 个变更、5 个恢复场景及 G4/G6/LH-001 协议草案 |
| [registry.schema.json](../acceptance/v0.1/registry.schema.json) | 注册内容和固定门槛的 JSON Schema 2020-12 |
| [freeze-manifest.schema.json](../acceptance/v0.1/freeze-manifest.schema.json) | 正式预注册所需的资产、运行器、检测器和环境绑定 |
| [observation.schema.json](../acceptance/v0.1/observation.schema.json) | 实际状态观测的结构与允许状态 |

注册文件是输入合同，观测文件是运行后证据。二者分开保存。草案中的 `creates_execution=false`、`contains_measurements=false` 描述该文件的性质，不是某个实际任务的运行状态。

输入的接受、几何完成、原生工程可重建及公开提交分别判断。可显示的公开工程版本必须有唯一权威身份，并固定 Goal、源规范、产物清单、验收和父版本；Worker 目录或模型自述不能作为公开版本。

## 2. G1～G7 的判定

| 门槛 | 固定判定 |
| --- | --- |
| G1 | 注册 10 个不同类型的自然语言任务；至少 8 个完整满足独立条件；所有声称完成的实体均几何有效 |
| G2 | 10 个交付对象均保留组件、参数及 Feature 关系；至少 8 个成功任务可无 Agent 修改参数并重建 |
| G3 | 20 个注册变更中至少 18 个最终状态正确；所有受影响依赖识别，无无关 Feature 误判；结果与全量正确重算在冻结公差内等价 |
| G4 | 1,000 个 Feature 的注册合成图，约定机器上单次失效传播 P95 严格小于 100 ms，准确率 100%；不包含 CAD 重算 |
| G5 | 5 个注册恢复场景全部通过；无重复发布，未验证候选不公开，不丢最后验证状态 |
| G6 | 一个至少 2 小时的端到端任务，至少 10 次有实际几何变化的验证提交，至少 1 次需求变化，人工不逐步操作 CAD |
| G7 | 每个成功案例有完整证据交付；另一开发者在干净环境复现至少 8 个成功案例 |

V0.1 只有在七项全部为 `passed` 时才能声明达标。部分通过只报告部分通过；单项单测、固定 IR 演示或几何运行器成功不能替代自然语言端到端验收。

G2 的分母固定为 10，不因 G1 出现失败而删掉案例。失败案例也须保留已形成的源状态和失败原因；缺失要求的可编辑源是未通过，不允许只提交图片后缩小分母。

## 3. 正式预注册的冻结过程

草案还不具有“已预注册”的资格。正式验收运行前完成以下步骤：

1. 独立准备并审阅每个案例的检测合同；为每个必需 `method_id` 绑定实际可执行检测器、输入 schema、构建摘要和适用范围。不能测量的必需条件阻止通过。
2. 为 20 个变更准备原生种子工程。审阅其参数、Feature 关系及实际几何；将草案里的语义角色展开为确切 Feature/Node ID 集合，填入独立 oracle 摘要并把 `binding_state` 设为 `bound_to_independent_seed`。
3. 独立制作依赖 oracle、几何 oracle 与变更后期望值。不能通过调用待测失效传播代码来生成其自己的期望集合。
4. 固定精度、比较策略、运行器、内核/验证器版本、超时/重试政策、硬件与进程资源配置；保存全部摘要。
5. 验证案例 ID 集合恰好为 `C01..C10`、`M01..M20`、`R01..R05`，每个案例条件 ID 唯一。JSON Schema 之外还要检查这些跨记录约束、种子/角色覆盖和所有引用闭包。
6. 生成新的冻结注册文件，设置实际冻结时间，再对其规范字节计算 SHA-256。源注册采用同项目的 RFC 8785 JCS 编码，不以 JSON 作者的键序和排版决定身份。
7. 创建冻结清单，固定注册摘要、35 个案例正文摘要、种子/角色绑定/oracle 摘要、检测器与运行器构建、机器和环境清单。由授权注册者登记后，验收执行引用该清单。

哈希引用保持单向：`种子与oracle → 冻结注册 → 冻结清单 → 观测报告`。注册文件不反向包含其冻结清单摘要，避免两份文件互相包含对方摘要产生不可解的自引用。

冻结后不能覆盖门槛、案例、检测方法或预期值。需要修订时创建新注册版本及新冻结清单，保留被替代清单和理由；旧结果继续绑定原输入，不能静默重新归类。不得在看过某次正式成绩后改阈值并继续沿用原成绩。

本目录不提供一份看似已执行的冻结清单；目前缺失的真实构建、机器、种子/oracle 绑定不能用示例 hash 补齐。

## 4. 自然语言案例与独立检测

10 个草案类型覆盖四孔板、旋转阶梯轴、指定外角圆角、孔口倒角、圆周孔阵列、线性鳍片、约束圆弧长槽、主参数驱动阶梯孔、共享定义刚性装配、跨组件引用门架。它们不是同一零件改尺寸后重复计数。

G1 的入口必须是注册的自然语言意图及允许的用户参考输入。规划者不能读取预制的参考 IR、参考实体或 oracle 文件后复制答案。案例中的尺寸和用户验收条件可以公开；生成答案的 Feature 编排和参考产物不属于规划输入。

运行环境必须落实这个边界，例如：规划沙箱只挂载任务意图、公开 Goal 合同及当前合法工程源；独立检测器才挂载 oracle。仅在提示词里写“不要看答案”不能作为隔离证据。

注册中的解析体积值来自用户尺寸的独立公式，不来自候选几何测量。体积与包围盒只承担相应条件，不能替代孔位、圆角半径、倒角、相切、接触、层级和干涉检查。例如 C05 即使体积正确，孔距或角度错误也必须未通过。

现有 `fixtures/mechanical/` 的三个参数化工程是开发回归样例。它们可以用于工程功能检查或独立种子准备，不能仅凭直接导入 IR 成功就计作上述自然语言案例成功。

每个成功案例还必须输出稳定的参数/角色绑定和无 Agent 编辑入口。G2 修改的是交付源中的受控参数或 Feature 参数，然后调用同一 Scene Kernel 重新构建。不能依赖原提示词、原 Agent 记忆、临时 Python 变量或开发者手工补文件。

## 5. 变更、失效集合与全量对照

每个变更以冻结种子开始，不在上一用例留下的隐含进程状态上继续。种子资产和预期角色绑定是输入，实际修改前的公开验证版本是恢复基线。

草案覆盖上游尺寸、局部圆角/倒角、阵列数量拓扑变化、约束草图尺寸、派生参数、跨组件随动、实例增删、元数据重命名，以及冲突目标和悬空引用。

对有效变更记录：

- 变更前后源版本、Goal 版本和 IR 摘要。
- 独立 oracle 的确切受影响集合，与实际识别集合的差集；两方向差集都为空才是准确。
- 实际执行几何求值的 Feature 集合、缓存命中及各自原因。重用未变化的几何不等于重新构造后恰好得到相同字节。
- 无关 Feature 的既有几何输出是否继续复用。Scene 名称或 STEP 元数据变化可以更新交付物，但不能因此把无关几何标记为失效。
- 同一最终源状态在独立执行命名空间内的全量正确重算结果，以及逐项几何等价检查。

全量对照不得读取增量执行的结果缓存作为答案。比较应包含适用的拓扑、尺寸、体积、实例位置及关系；字节 hash 相同可证明同一字节，不足以定义不同序列化结果的几何等价。

M18/M19 的目标结果是拒绝并保持最后验证状态，不是新建几何成功。它们的权威状态失效集合为空；候选诊断中潜在受影响集合单独记录。汇总必须分别列出有效变更成功、正确拒绝和错误/未知，不能把正确拒绝描述成成功建模。

角色名如 `stock.extrude` 目前只是草案绑定要求，不是已经存在的 Feature ID。冻结时必须展开别名和 `all_existing_geometry_features` 等集合占位符，形成确切、不可变的 ID 集合；不能在运行后根据实际脏集合反向补 oracle。

## 6. G4 性能边界

注册图包含恰好 1,000 个 Feature，具有链、共享上游、扇出和汇合。图和 1,000 个固定查询都有独立期望集合；初始加载、索引构建和生产调用入口在冻结清单中明确。

预热 100 次，再按固定顺序测量 1,000 次。计时从生产 API 对规范化变更定位种子开始，到确切失效 ID 及解释绑定形成结束。若该生产 API 每次内部重建索引，这个成本也在计时内；初始索引建立另行报告。排除实际 CAD 求值、网络、磁盘传输和报告序列化。

保留每个原始时长，用 nearest-rank 计算：将 N 个样本升序排列，选择 `ceil(0.95*N)-1` 的零基索引。`P95=100 ms` 不通过。所有结果集合逐项等于独立 oracle 才能报告准确率 100%，不能用平均命中率掩盖漏项。

固定机器清单包含 OS、架构、CPU、逻辑核数、内存、功耗策略、编译器、构建模式、进程限制和单调时钟。不能只选快查询、删除慢样本、使用仅为 benchmark 存在的快路径，或换机器后沿用原性能声明。

## 7. G5 恢复情境

五类分别是：验证接纳前 Worker 崩溃；权威提交成功但回执丢失；重复/乱序及失权 Attempt 回写；执行中需求修改并遇并发工程变更；模型切换、服务重启和调用超时。

每次故障前，先独立读取最后公开验证版本及全部绑定；故障后重新读取权威状态，检查公开版本数量、代数、候选归属、拒绝原因和可编辑源重建。只检查 HTTP 最后返回成功或进程重新启动不算恢复通过。

同请求的回执重放应返回原完成事实，不能重复发布；旧执行和旧目标不能借重试恢复新的发布权。超时或服务不可达产生的不确定结果需要查询/重送稳定身份，不能直接标成成功或当成从未发生。

R05 的真实模型切换要求两个可用且身份不同的实际模型配置，可来自同一提供方。没有凭据或只有脚本化传输时，相关证据为不足，不能改名为已完成真实模型切换。无论模型是否可用，原生工程都必须可以无原 Agent/原提示词重建。

## 8. G6 与 LH-001 的时间真实性

G6 不是“守着一个进程两小时”。真实运行至少 2 小时，至少有 10 次唯一权威验证提交，且每次计数的提交都改变实际几何。新 UUID、重命名、STEP 头改变、渲染刷新和未参与几何的参数变化不计。

记录实际起止时间、单调经过时间、每次有效提交和按类别划分的工作区间。规划、求值、独立检测、恢复和等待已登记依赖可以构成可解释的推进；空队列、人工插入 sleep、只有心跳或等待人逐步操作 CAD 不能用于凑时长。此条件不要求 CPU 连续满载。

至少一次外部需求变化必须形成新的 Goal 版本，并改变后续验收条件。允许人提交自然语言变更和明确记录的合同澄清；不允许人选择每个 CAD 操作、手工编辑几何、修补隐藏状态后仍计为无人逐步干预。

LH-001 的 72 小时另有完整城堡目标，超出本周最低门槛。它需要主要组件可编辑、实际约束检测、真实需求修改和中断、验证成果继承及可查询的完成/未完成/候选采纳状态。写出协议、启动后台服务、安排提醒或让空进程存活都不等于任务已经执行或通过。

## 9. 统一交付包与干净环境复现

每个成功案例的证据包至少包括：

```text
input/          注册案例、原始意图、用户参考输入及摘要
goal/           目标各版本、条件绑定、待确认/冲突/未知记录
source/         可编辑原生工程、参数、Scene与Feature关系
geometry/       实际BREP、STEP及其摘要
versions/       公开提交、父关系、差异、候选采纳/拒绝记录
verification/   原生/STEP/空间关系报告、方法与构建身份
execution/      Plan、Attempt、故障、恢复和模型切换的身份记录
reproduction/   无Agent重建/编辑/导出命令、环境锁与所需许可证
case-result.json
```

原始日志可以很大，清单必须闭合且可校验。秘密凭据不进入证据包。结果引用固定资产，不能把可变 URL 或 Worker 临时目录当作可复核交付。

干净复现使用另一开发者、全新声明环境和空的项目缓存。按包内命令重开源、重建、检查、修改参数、导出并重新检测；记录环境与全部输出摘要。仅复制已生成 STEP、使用原工作目录或开发者手动修补隐含状态均不满足 G7。

模型服务不可用不应阻止从可编辑源重建；若另行声称可从自然语言再次生成，则还须保留对应实际模型执行证据，不能与无 Agent 复现混为一项。

## 10. 观测状态和汇总一致性

报告状态只能是 `passed`（通过）、`failed`（未通过）、`insufficient_evidence`（证据不足）。草案/冻结是输入注册阶段，不是验收观测状态。

`observation.schema.json` 分别记录目标版本、已验证完成、几何有效性、可编辑性、增量准确性、失效传播性能、恢复、自主跨度、独立复现、证据与未解决阻碍。指标使用有定义的分子/分母、计数和真实时长；没有数据时为 `null`，不能填零或猜测百分比。

汇总器必须额外检查跨字段一致性：分子不超过分母；分母等于冻结注册范围；G1 所有完成声明都能追到几何检查；G2 不减少失败样例分母；G7 完整证据包覆盖每个成功案例，复现数量等于独立成功案例 ID 数量且都来自 G1 成功集合；G4 精确结果数量等于实测数量；G5 重复/未验证发布为零；G6 提交 ID 唯一且均有实际几何变化；每个 `passed` 都引用存在且绑定正确的证据。

JSON Schema 验证只检查记录结构，不证明这些事实或数值真实。能力已经实现但没有冻结验收证据时仍应报告证据不足；有明确反例、未实现必需路径或已观察到违约则报告未通过。所有失败/未知条件保留在交付包和状态投影中。
